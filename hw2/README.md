# HW2: ускорение претрейна Qwen3 1B

Я продолжил работать с моделью из первого задания и проверил, как разные оптимизации влияют на скорость, память и loss на одной A100 80 GB. Главная метрика в этом задании — полезные токены в секунду.

Лучший результат по скорости дал режим `FlashAttention2 + packing`. Два одинаковых запуска с batch 32 показали 22 323 и 22 359 токенов/с; среднее — **22 341 токен/с**, или **3.18x** относительно бейзлайна. Packing с batch 48 сохранил практически ту же скорость, но получил более низкий `validation_loss`. Более экономный вариант `FlashAttention2 + padding-free + batch 64` дал **20 124 токена/с**, зато занял примерно вдвое меньше выделенной GPU-памяти и получил лучший loss среди финальных запусков.

## Сетап

Все запуски сделаны с нуля на одной и той же GPU. Модель, данные, разбиение, максимальную длину, optimizer, learning rate, scheduler, seed и код подсчёта метрик я не менял.

Бейзлайн и финальные конфигурации обучались по 300 секунд. Для первичного отбора оптимизаций я использовал запуски примерно по 60 секунд.

Скорость считается кодом из шаблона после исключения первых 10 прогревочных шагов. Ускорение считаю так:

```text
speedup = tokens_per_second эксперимента / tokens_per_second бейзлайна
```

## Отбор оптимизаций

В таблице `peak allocated / reserved` — пиковая память, которую PyTorch соответственно занял тензорами и зарезервировал у CUDA allocator. Все ускорения посчитаны относительно полного бейзлайна с 7 035.5 токена/с.

| Бейзлайн | SDPA | 32 / 2 | 300.23 | 7 035.5 | 1.00x | 41.24 / 43.44 | 367 | 6.6065 |
| Batch 48 | SDPA | 48 / 1 | 60.03 | 6 704.5 | 0.95x | 56.46 / 60.39 | 92 | 8.2773 |
| Checkpointing | SDPA, activation checkpointing | 64 / 1 | 61.30 | 5 071.7 | 0.72x | 25.81 / 27.43 | 54 | 8.5042 |
| FlashAttention2 | FlashAttention2 | 32 / 2 | 60.66 | 7 662.5 | 1.09x | 39.17 / 41.60 | 79 | 8.3134 |
| Packing | FlashAttention2, packing | 32 / 2 | 60.84 | **22 597.9** | **3.21x** | 40.15 / 76.20 | 42 | 8.7551 |
| Packing + batch 48 | FlashAttention2, packing | 48 / 1 | 60.91 | 22 372.2 | 3.18x | 54.81 / 76.93 | 56 | 8.2732 |
| Padding-free | FlashAttention2, padding-free | 32 / 2 | 60.11 | 19 413.3 | 2.76x | **15.11 / 21.24** | 202 | 7.6123 |

Всего я проверил пять механизмов: изменение batch size, activation checkpointing, FlashAttention2, packing и padding-free. Отдельно протестированы сочетания FlashAttention2 с packing, padding-free и разными batch size. Таймер останавливает обучение после завершения текущего шага, поэтому фактическое время иногда чуть больше заданных 60 или 300 секунд.

Validation loss коротких и полных запусков нельзя напрямую сравнивать: они обучались разное время и успели сделать разное число шагов. Здесь loss нужен как проверка, что обучение не развалилось; итоговые варианты ниже сравниваются уже на одинаковых 300 секундах.

## Финальные запуски на 300 секунд

| Конфигурация | Время, с | Токенов/с | Ускорение | Полезных токенов | Peak allocated / reserved, GiB | Шагов | Validation loss |
|---|---:|---:|---:|---:|---:|---:|---:|
| Бейзлайн: SDPA, batch 32 / 2 | 300.23 | 7 035.5 | 1.00x | 2 089 441 | 41.24 / 43.44 | 367 | 6.6065 |
| FlashAttention2 + packing, batch 32 / 2 | 300.48 | 22 323.3 | 3.17x | 6 681 427 | 40.17 / 76.20 | 209 | 6.6166 |
| Повтор packing, batch 32 / 2 | 301.40 | **22 358.7** | **3.18x** | **6 713 693** | 40.17 / 76.20 | 210 | 6.6380 |
| FlashAttention2 + packing, batch 48 / 1 | 300.71 | 22 306.9 | 3.17x | 6 689 499 | 54.93 / 76.93 | 279 | 6.0243 |
| FlashAttention2 + padding-free, batch 64 / 1 | 300.18 | 20 123.8 | 2.86x | 6 020 746 | **20.45 / 39.72** | **1 051** | **5.0514** |

Два одинаковых запуска packing с batch 32 отличаются по throughput всего на 0.16%. Их средняя скорость — 22 341 токен/с, то есть результат воспроизводится и не выглядит случайным выбросом.

По главной метрике задания итоговой считаю конфигурацию с packing и batch 32. Она в среднем обработала в 3.18 раза больше полезных токенов, чем бейзлайн. В `train.py` именно этот режим стоит по умолчанию.

Batch 48 оказался практически равен ему по скорости: разница со средним batch 32 всего 0.15%. При этом он сделал 279 optimizer steps вместо 209–210 и снизил validation loss до 6.0243. Цена этого улучшения — рост allocated-памяти с 40.17 до 54.93 GiB. Поэтому batch 48 — более сбалансированный вариант, но не новый победитель по главной метрике.

При этом padding-free — практичная альтернатива, если важнее не максимальный throughput, а запас памяти и loss за те же пять минут. Она немного медленнее packing, но требует примерно вдвое меньше `allocated`-памяти и делает намного больше optimizer steps.

## Что получилось заметить

1. **Один только FlashAttention2 уже помогает.** Скорость выросла с 7 035.5 до 7 662.5 токена/с, то есть на 8.9%, а выделенная память немного снизилась.
2. **Простое увеличение batch не ускорило обучение.** Batch 48 оказался на 4.7% медленнее бейзлайна и занял больше памяти. Batch 64 без других оптимизаций упал с OOM.
3. **Activation checkpointing решает проблему памяти, но платит скоростью.** С ним batch 64 поместился и занял только 25.81 GiB allocated-памяти, однако throughput снизился на 27.9% относительно бейзлайна из-за повторных вычислений на backward.
4. **Packing дал максимальный throughput.** Он убирает большую часть padding и заполняет каждый блок реальными токенами. Сочетание с FlashAttention2 оказалось примерно в 3.2 раза быстрее бейзлайна.
5. **Batch 48 поверх packing почти не изменил throughput, но улучшил loss.** Его скорость отличается от среднего результата batch 32 всего на 0.15%. За те же пять минут он сделал 279 обновлений вместо 209–210 и снизил validation loss с 6.6166–6.6380 до 6.0243. При этом allocated-память выросла на 14.76 GiB, поэтому для чистого throughput я оставил batch 32.
6. **Padding-free оказался лучшим компромиссом между скоростью и памятью.** Уже на batch 32 он дал 19 413 токенов/с при 15.11 GiB allocated-памяти. Batch 64 поднял скорость до 20 461 токена/с и всё ещё оставил большой запас памяти.
7. **Количество optimizer steps важно для интерпретации loss.** При packing с batch 32 один шаг содержит намного больше полезных токенов, поэтому за 300 секунд получилось только 209–210 шагов и почти весь запуск занял фиксированный warmup из 200 шагов. Padding-free сделал 1 051 шаг и успел дольше обучаться на полном learning rate, поэтому его validation loss заметно лучше. Scheduler менять по условию было нельзя.

## Неудачные пробы

- `SDPA + batch 64` упал с OOM: к моменту ошибки процесс занимал около 75.4 GiB.
- `use_liger_kernel=True` не запустился из-за ошибки Triton `device kernel image is invalid`.
- `torch_compile=True` упал с той же ошибкой при компиляции CUDA-ядра через Triton. Это ограничение текущей связки драйвера, CUDA и Triton, а не ухудшение метрики, поэтому незавершённые запуски я не добавлял в таблицу успешных экспериментов.

## Кольцевые коммуникации

В `collectives.py` реализованы три операции для CPU и Gloo:

- `ring_reduce_scatter`: каждый процесс передаёт следующий chunk соседу справа, принимает chunk слева и суммирует его;
- `ring_all_gather`: готовые шарды проходят по тому же кольцу, после чего собираются через `torch.cat`;
- `ring_all_reduce`: последовательно вызывает две предыдущие операции, поэтому на всех процессах получается полная сумма.

Входные тензоры не изменяются. Реализация проверена сравнением со встроенными `torch.distributed`-операциями для нескольких размеров тензора на 2 и 4 процессах. Обе проверки завершились успешно; вывод сохранён в исполненном `communications.ipynb`.

## Структура папки

- `train.py` — итоговый код обучения; параметры экспериментов можно менять через переменные окружения;
- `results/*/summary.json` — метрики всех успешных запусков;
- `communications.ipynb` — заполненный и исполненный ноутбук;

## Как воспроизвести

Из папки `hw2` нужно собрать образ:

```bash
docker build -t qwen-hw2 .
```

Финальная конфигурация с packing уже стоит по умолчанию:

```bash
docker run --rm --gpus all --shm-size=16g \
  -v "$PWD:/app" -w /app \
  qwen-hw2 python train.py
```

Например, бейзлайн запускается так:

```bash
docker run --rm --gpus all --shm-size=16g \
  -v "$PWD:/app" -w /app \
  -e RUN_NAME=baseline \
  -e ATTENTION=sdpa \
  -e PACKING=0 \
  qwen-hw2 python train.py
```

Данные подготавливаются автоматически при первом запуске. Для нового эксперимента нужно задавать новый `RUN_NAME`, потому что код специально не перезаписывает существующую папку с результатами.

Проверки коммуникаций без ноутбука:

```bash
python -m torch.distributed.run --standalone --nproc-per-node=2 check.py
python -m torch.distributed.run --standalone --nproc-per-node=4 check.py
```

## Вывод

Лучший способ ускорить этот конкретный запуск — не просто увеличивать batch, а убрать лишний padding и использовать более эффективный attention. `FlashAttention2 + packing` с batch 32 воспроизводимо дал в среднем **22 341 токен/с и ускорение 3.18x**. Batch 48 сохранил ту же скорость в пределах разброса и улучшил validation loss до 6.0243, поэтому это лучший компромисс между throughput и качеством. `FlashAttention2 + padding-free` немного проиграл по скорости, но оказался заметно экономнее по памяти и получил лучший loss, поэтому для более длинного обучения я бы выбрал именно его.
